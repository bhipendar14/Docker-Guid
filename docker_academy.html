MODULE 01

Docker fundamentals

Docker is a platform for building, distributing and running applications in containers.

Container

An isolated running process (or group of processes) with its own filesystem view, networking and resource controls. It shares the host kernel.

Image

A read-only, layered template used to create containers. An image is not itself a running application.

Dockerfile

A text file containing instructions to build an image, such as FROM, RUN and COPY.

Registry

A service that stores and distributes images. Docker Hub is a popular public registry; private registries are also common.

Containers vs virtual machines

ContainersVirtual machines
Share the host OS kernel (on Linux).Each VM runs its own guest OS kernel.
Usually start quickly and use fewer resources.Usually have more overhead and boot a full guest OS.
Isolate processes using OS-level features.Virtualize hardware through a hypervisor.
Isolation is strong but not identical to a separate VM.Often provide a stronger OS boundary, depending on configuration.
Remember: A container is not a tiny virtual machine. It uses OS-level isolation and shares a kernel. On Windows or macOS, Docker Desktop commonly runs Linux containers inside a lightweight Linux VM.

Why Docker?

  • Consistent packaging across development, testing and production.
  • Repeatable builds and easier deployment.
  • Process isolation, resource limits and portable image distribution.
  • Supports microservices and CI/CD workflows.
MODULE 02

Docker architecture

The classic Docker Engine architecture uses a client-server model.

Docker CLI (client)

What you type, e.g. docker ps. Sends API requests to the daemon.

Docker daemon (dockerd)

Manages Docker objects such as images, containers, networks and volumes.

Docker Engine API

Interface used by clients to communicate with the daemon, commonly over a Unix socket or configured endpoint.

containerd / OCI runtime

Lower-level components help manage container lifecycle and start processes. runc is a widely used OCI runtime.

YOU → docker CLI → Docker Engine API → dockerd
                                  ↓
                    images / containers / networks / volumes
                                  ↓
                         containerd → runc

That diagram is simplified: the exact internals vary by version and setup. Docker Desktop adds desktop-managed components and a Linux VM for Linux containers on macOS/Windows.

Docker objects

  • Image: immutable template / layers.
  • Container: created from an image, with a writable container layer.
  • Network: connectivity between containers and external networks.
  • Volume: persistent data managed by Docker.
  • Context: configuration selecting which Docker endpoint the CLI talks to.
Exam trap: The CLI is not the daemon. A client command usually asks the daemon to perform work; the CLI can also target a remote daemon via a context or endpoint.
MODULE 03

Images, tags and layers

Images are built from layers, which enable caching and reuse.

  • Most Docker images consist of ordered, read-only layers.
  • A container adds a writable layer on top of its image layers.
  • Multiple containers can share the same underlying image layers.
  • Changing a file in a container's writable layer does not change the original image.
  • A tag such as nginx:1.27 is a human-friendly reference; tags can move. A digest identifies content more precisely.

Image naming

[registry/][namespace/]repository[:tag][@digest]
docker.io/library/nginx:latest
ghcr.io/org/my-app:1.4.2

If no registry is specified, Docker commonly defaults to Docker Hub. If a tag is omitted, the default tag is generally latest—but latest does not necessarily mean newest or safest.

Build and inspect

docker pull nginx:alpine
docker images
docker image ls
docker image inspect nginx:alpine
docker history nginx:alpine
docker build -t my-app:1.0 .
docker tag my-app:1.0 username/my-app:1.0
Important: Removing a tag does not necessarily delete the image's underlying layers if another tag or container still references them. Avoid relying on latest for reproducible production deployments.
MODULE 04

Containers and their lifecycle

A container is created from an image and runs its configured main process.

docker create --name demo nginx
docker start demo
docker ps                 # running containers
docker ps -a              # all containers, including stopped
docker stop demo          # graceful stop, then kill after timeout
docker start demo         # start an existing stopped container
docker restart demo
docker rm demo            # remove a stopped container
docker run --name web -d -p 8080:80 nginx

What does docker run do?

Conceptually, it creates and starts a new container. Options can configure ports, environment, volumes, networks, restart policy and more.

OptionMeaningExample
-dDetached/background modedocker run -d nginx
-itInteractive TTY (commonly combined)docker run -it ubuntu sh
--nameSet a human-readable container name--name web
--rmAutomatically remove container after it exitsdocker run --rm alpine echo hi
-p HOST:CONTAINERPublish a container port on the host-p 8080:80
-eSet an environment variable-e MODE=dev
--mount / -vMount storage into the container-v data:/data

Process and data behaviour

  • When a container's main process exits, the container stops; it is not automatically deleted unless configured (e.g. --rm).
  • docker exec runs an additional command inside a running container.
  • docker attach connects your terminal to the container's main process streams.
  • docker logs displays logs available from the container logging configuration.
  • Stopping/removing a container does not remove a separately managed named volume by default.

Useful operational patterns

# Follow logs and show recent lines
docker logs --tail 100 -f web

# Open a shell in a running container (if shell exists)
docker exec -it web sh

# Inspect port mappings
docker port web

# Show all containers, including exited ones
docker ps -a

# Remove stopped containers (review before confirming)
docker container prune

# Show Docker resource usage
docker system df
Destructive commands: docker system prune, docker volume prune, docker rm -f and docker volume rm can remove resources or data. Check what will be deleted before confirming.
MODULE 06

Dockerfile essentials

A Dockerfile describes how to build an image. The build context supplies files the build can access.

InstructionPurposeKey detail
FROMChoose a base imageUsually begins a build stage.
WORKDIRSet working directoryCreates it if needed; affects later instructions.
COPYCopy files from build contextUsually preferred for straightforward local file copying.
ADDCopy files, with extra featuresCan handle local tar extraction and supported remote sources; use COPY unless extra behavior is needed.
RUNExecute build-time commandCreates image-layer changes.
ENVSet environment variable in imageMay persist in image metadata/config; don't put secrets here.
ARGBuild-time variableNot designed for secrets; values may be exposed in build metadata/history.
EXPOSEDocument intended listening portDoes not publish a port on the host.
CMDDefault command/argumentsCan be overridden at runtime.
ENTRYPOINTConfigure executableOften combined with CMD for default arguments.
USERSet user for later runtime commandsPrefer non-root when practical.
VOLUMEDeclare mount pointDoes not itself provide a backup strategy.
HEALTHCHECKDefine health probeHealth status is distinct from process running state.
LABELAdd metadataUseful for ownership and version metadata.

Example Dockerfile

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
ENV NODE_ENV=production
USER node
EXPOSE 3000
CMD ["node", "server.js"]

Example only: it assumes your project has a compatible package-lock.json, server.js, and a node user in the selected base image. Adapt to your application.

CMD vs ENTRYPOINT

CMD

Supplies the default command or default arguments. A command supplied after the image name to docker run normally replaces CMD.

ENTRYPOINT

Sets the executable that runs as the container process. Runtime arguments are commonly passed to it; use exec form for predictable signal handling.

Build context and cache

docker build -t demo:1.0 .
# . is the build context
# .dockerignore excludes unnecessary files from the context

Order instructions to improve cache reuse: copy dependency manifests and install dependencies before copying frequently changing source files. Use multi-stage builds to keep build tools out of the final image when appropriate.

MODULE 07

Volumes, bind mounts and persistence

A container's writable layer is ephemeral compared with dedicated storage.

Volume

Managed by Docker. Good default for persistent application data. Can be named or anonymous.

Bind mount

Maps a specific host path or file into a container. Useful for development and sharing host files.

tmpfs mount

Stores data in host memory, not persistently on disk. Available in supported Linux environments.

Container layer

Writable changes tied to the container lifecycle. Removing the container removes this layer.

# Create and inspect a named volume
docker volume create app-data
docker volume ls
docker volume inspect app-data

# Mount named volume at /var/lib/app
docker run -d --name app --mount source=app-data,target=/var/lib/app nginx

# Bind mount (host path syntax varies by OS)
docker run --mount type=bind,source=/absolute/host/path,target=/app nginx

# Remove a volume (only if no longer needed)
docker volume rm app-data
Exam rule: Volumes are usually the recommended way to persist container-generated data. Bind mounts expose a chosen host path. Removing a container normally leaves named volumes in place.

Backups still matter: persistence is not the same as backup, replication or disaster recovery.

MODULE 08

Docker networking and ports

Networks let containers communicate. Published ports let traffic reach a container through a host port.

Network typeTypical useRemember
bridgeCommon default for standalone containersUser-defined bridges provide automatic DNS resolution between attached containers by name.
hostUse host network namespace (platform-dependent)Port publishing is generally unnecessary/ignored in host mode.
noneNo normal container network connectivityLoopback remains available inside the container.
overlayConnect services across Docker Swarm nodesTypically used for multi-host networks.
macvlanGive containers a MAC address on a physical networkRequires network infrastructure/configuration.
docker network ls
docker network create app-net
docker network inspect app-net
docker run -d --name db --network app-net postgres
docker run -d --name api --network app-net my-api

# Publish host port 8080 to container port 80
docker run -d -p 8080:80 --name web nginx

Port mapping syntax: -p HOST_PORT:CONTAINER_PORT. Here, host port 8080 forwards to port 80 inside the container. EXPOSE 80 in a Dockerfile is documentation; it does not create this mapping.

Common trap: Containers on the same user-defined bridge network can typically resolve one another by container name. From one container, localhost means that same container, not another container or the host.
MODULE 09

Docker Compose

Compose defines and manages a multi-container application using a YAML file, commonly compose.yaml.

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      - app
  app:
    build: .
    environment:
      APP_MODE: production
    volumes:
      - app-data:/data
volumes:
  app-data:

Common Compose commands

docker compose up             # create/start services
docker compose up -d          # detached
docker compose ps              # list project containers
docker compose logs -f         # follow logs
docker compose exec app sh     # run command in service container
docker compose build           # build configured images
docker compose down            # stop/remove project containers and networks
docker compose down -v         # also remove declared named volumes: use caution
  • Services describe application components; Compose creates/manages their containers, networks and configured volumes.
  • depends_on controls dependency/start order; by itself it does not guarantee that a dependency is ready to accept requests. Health checks and suitable conditions/logic may be needed.
  • Compose is for defining and operating multi-container apps; it is not the same as Docker Swarm orchestration.
  • Compose V2 uses the docker compose CLI plugin syntax. Older Compose V1 used docker-compose.
MODULE 10

Security and best practices

  • Use trusted, maintained base images; pin versions or digests when reproducibility matters.
  • Run as a non-root user where practical; minimize Linux capabilities and privilege.
  • Avoid --privileged unless there is a specific, understood need.
  • Never bake passwords, API keys or private keys into Dockerfiles, image layers, or source control. Use a suitable secret-management mechanism.
  • Keep images small: use appropriate base images, multi-stage builds and .dockerignore.
  • Patch the host, Docker Engine, base images and dependencies. Scan images and review provenance where available.
  • Use resource limits where appropriate; don't assume containers automatically have safe CPU/memory limits.
  • Publish only required ports and restrict access. Understand that published ports may be reachable beyond the local machine depending on configuration.
  • Use read-only filesystems and drop capabilities when compatible with the workload.
  • Do not treat a container boundary as a replacement for host security or VM isolation in every threat model.
Secret trap: ARG and ENV are not secure secret stores. BuildKit secret mounts or a dedicated secret manager are better options for sensitive build/runtime secrets.
MODULE 11

Registries, troubleshooting and cleanup

Registry workflow

docker login
docker pull nginx:alpine
docker tag my-app:1.0 username/my-app:1.0
docker push username/my-app:1.0
docker logout

A registry stores images. A repository groups image versions/tags. Authentication proves identity; authorization determines what you can access. Never paste registry passwords or tokens into shared logs.

First-line troubleshooting

docker ps -a                 # is it running or exited?
docker logs my-container      # what did the app print?
docker inspect my-container   # configuration and state
docker exec -it my-container sh
docker stats                  # resource usage
docker port my-container      # published ports
docker network ls
docker volume ls
docker system df              # disk usage
SymptomPossible cause / next check
Container exits immediatelyMain process ended or failed. Check docker logs, exit code and command.
Cannot connect to appCheck app bind address, internal port, -p mapping, firewall and network.
Image pull deniedCheck image name/tag, registry reachability, login and permissions.
Build cannot find fileCheck build context, path, .dockerignore and COPY source paths.
Out of disk spaceCheck docker system df; remove only confirmed-unused resources.
Container cannot resolve another nameCheck both containers share a user-defined network and DNS/name configuration.

Save vs export — a classic MCQ

docker save

Saves image(s), including layers and image metadata, to an archive. Pair with docker load.

docker export

Exports a container filesystem as a tar stream; it does not preserve image layers/history. Pair with docker import.

MODULE 12

Swarm, health checks, resources and advanced concepts

Docker Swarm

  • Swarm is Docker Engine's native clustering/orchestration mode.
  • Manager nodes maintain cluster state and schedule tasks; worker nodes run assigned tasks. Managers can also run workloads.
  • A service defines desired state, such as image and replica count. A task is a unit of work scheduled by Swarm, usually a container.
  • Swarm supports service scaling, rolling updates, overlay networks and service discovery.
  • Swarm mode is different from Kubernetes and is not required for ordinary single-host Docker use.
docker swarm init
docker node ls                 # run on a manager
docker service create --name web --replicas 3 -p 8080:80 nginx
docker service ls
docker service scale web=5
docker service rm web

Health and restart policies

  • A process can be running but unhealthy. Health status is distinct from container running state.
  • HEALTHCHECK defines how Docker tests container health; the app image must provide a suitable probe command.
  • Restart policies include no, on-failure, always and unless-stopped. They control restart behavior, not application correctness.
  • Resource controls can set CPU/memory limits, e.g. --memory and --cpus, subject to platform support.
docker run -d --name limited --memory=512m --cpus=1 nginx
docker update --restart unless-stopped web

BuildKit and multi-stage builds

  • BuildKit is a modern build backend with features such as improved caching, parallel build steps, and secret/SSH mounts.
  • Multi-stage builds use multiple FROM stages and copy only selected artifacts into a final stage.
  • Build cache improves speed; cache is not a guarantee that a build will always reuse every step.
